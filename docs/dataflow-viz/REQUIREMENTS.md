# MN-Core データ移動可視化サイト 要件定義

## 1. 目的

MN-Core 2 の VSM プログラムが、メモリ階層の中で大量のデータをどう動かしているかを、SVG アニメーションで見えるようにする。

最終的な目的は、よりよいグラフコンパイラ（`fx_export`）を作ることである。
そのため、ステップ数は公式ジャッジと同じ数え方をし、ハザードや並列発行の制約がどこでどう効いているかまで読み取れるようにする。

既存の `gif_generation/` にある公式動画（`.smv`）は、命令1個の挙動を示す短いデモである。
本サイトは、プログラム全体を通したデータの流れを扱う。

| 用途 | 欲しいこと |
|---|---|
| 自分の解答・コンパイラ出力のデバッグ | どのステップで、どの値が、どこから、どの演算器を通って、どこへ入ったかを追える |
| 性能のボトルネック把握 | 公式スコア、nop が入った理由、並列発行できなかった理由、階層ごとの混み具合が分かる |
| 学習・説明用 | 転送パターンをスクロールで読み進める解説として見せられる |

## 2. 対象のハードウェアモデル

可視化する階層は次のとおり（`docs/mncore_llm` の 1.1 構成による）。

```
Host ── PDM(×4 グループ) ── DRAM(×4)
           │
        L2BM (×8, 2 個ずつ 4 グループ)
           │
        L1BM (×64, L2B あたり 8)
           │
        MAB (×1,024, L1B あたり 16) ── MAU（行列レジスタ $x / $y）
           │
        PE (×4,096, MAB あたり 4): LM0 / LM1 / GRF0 / GRF1 / T / マスクレジスタ
                                   ALU、各種フォワーディング（$aluf / $mauf / $lbf / $mreadf）
```

- 階層の個数や容量は設定データとして持ち、コードに直接書かない。
- PE の内部（ローカルメモリ、レジスタ、ALU、MAU、フォワーディング経路）も対象に含める。
  `problems/*/main.vsm` は PE 内の転送（`$lm`→`$aluf`→`$ly`→`gmmul` など）が大半を占めるため。

## 3. 時間の単位：公式準拠

### 3.1 スコア

公式ジャッジ（`judge/judge-py/judge.py`）のスコアは次のとおり決まる。

- VSM を公式アセンブラ `assemble3 --instruction-mode flat` で機械語に変換する。
- 出力のうち `j` 行（PE 命令語）と `m` 行（MV 命令語）の数を足したものがスコアになる。
- `wait` による実行時の停止はスコアに含まれない。
  スコアは実行時間ではなく、発行される命令語の数である。

### 3.2 ステップとサイクル

仕様（`docs/mncore_llm` の 3.6 節）から、次のとおり扱う。

- 1 PE 命令文（セミコロンで並べた式を含む1行）が1ステップになる。
- 1ステップは4サイクルである。
- `nop` は1ステップ、`nop/N` は N ステップになる。
- タイムラインの最小単位はステップとし、ステップを展開するとサイクル単位の様子を見られるようにする。
  ハザードはサイクル単位で決まるため（例：PE メモリへの書き込みは完了まで6サイクルかかる）。

### 3.3 公式アセンブラとの照合

- 各 VSM 行が何個の `j` / `m` 語になるかは、自前の解析の結果を公式アセンブラの出力と突き合わせて確認する。
  自前の数え方が公式とずれていれば、ビルドやテストの段階でエラーにする。
- 公式アセンブラは Docker 経由で使う（`fx_export/tools/assembler`）。
  サイトは静的にしたいので、照合はブラウザではなく、前処理の CLI とテストで行う。

## 4. 入力と解析

### 4.1 入力

- 解答の VSM：`problems/*/main.vsm` と、`fx_export` が出力する VSM。
- テストケース：`problems/*/testcase.vsm`。
  冒頭の `d set` に、入力値とその配置（例：`@LM0`、`(8_L2B:1, 32:1), ...`）が書かれている。
  これを初期状態として使う。

VSM は制御構造のない、1本の命令列である。
そのため、各ステップで何が起きるかを静的にすべて復元できる。

### 4.2 解析の内容

1. 命令列を読み込み、各行をステップに割り当てる（3.2 節の規則に従う）。
2. 各命令式を「イベント」に変換する。
   - 送り元・送り先：階層、ユニットの集合、アドレス範囲、オペランド（`$lm0v` など）
   - 経由する演算器：ALU / MAU と演算の種類、フォワーディング経路
   - 語数、精度、転送の種類（unicast / bcast / distrib / concat / reduce / multicast など）
   - マスクの指定（書き込みマスク、ゼロフラッシュマスク）
3. 値を追跡する（4.3 節）。
4. ハザードと並列発行の制約を判定する（4.4 節）。
5. 解析できない命令は「未対応」として一覧に出し、そのステップは空けたまま処理を続ける。

### 4.3 値の追跡

二つの追跡を行う。どちらも PE のレジスタに入るまでの経路をすべて持つ。

1. **出どころの追跡（来歴）**
   - どの値が、どの入力要素・即値から、どの経路（ロード → ALU / MAU → フォワーディング → 書き込み）を通ってきたか。
   - 任意のアドレスをクリックすると、その値ができるまでの依存関係を、ステップをさかのぼって表示する。
2. **数値の追跡**
   - テストケースの入力値から自前でシミュレーションし、各レジスタやメモリの値を表示する。
   - 結果はテストケースの期待値と照合する。
     必要なら、エミュレータの `d get` の出力とも照合して、シミュレーションの誤りを見つける。

### 4.4 競合と制約の判定

「なぜここに nop が必要か」「なぜこの2命令を同じ行に並べられないか」を説明できるようにする。

- **ハザード**（3.6.3 節）：データ競合とポート衝突を区別して判定する。
  - 例：LM0/LM1 への書き込みのあとは、ポート衝突のため2ステップ空ける。
  - 例：GRF0/GRF1 や T レジスタへの書き込みのあとは、データ競合のため1ステップ空ける。
  - L1BM/L2BM の転送どうしの組み合わせ（3.6.3.1〜3.6.3.8）も対象にする。
- **並列発行の条件**（3.6.4 節）：同じグループの命令式の重複、MAU 3グループの組み合わせ、同じ PE オペランドへの書き込みの重複、読み出しアドレスの一致など。
- **MV 命令と `wait`**：タグごとの待ち合わせの関係を表示する。
  MV の実行サイクル数は静的には決まらないので、待ち合わせの関係だけを示し、時間は推定しない。

表示では次のことができるようにする。

- 各 nop について、それがどの書き込みとどの読み出しの間の、どの種類の競合を避けているかを表示する。
- 逆に、競合がないのに入っている nop を「削れる候補」として示す（コンパイラ改善の手がかり）。
- 判定の規則は、アセンブラのエラーと同じ結果になるかをテストで確かめる。

### 4.5 解析結果の形式

- イベント列、値の来歴、競合の判定結果を JSON に書き出す。描画はこの JSON だけを入力とし、パーサとは切り離す。
- 書き出した JSON はそのまま静的ファイルとして配信でき、Story モードでも使い回せる。

### 4.6 対応命令の範囲（段階的に広げる）

- **M1:** PE 内の転送と演算（`$lm` / `$ln` / `$r` / `$s` / `$t` / `$aluf` / `$mauf`）、行列レジスタ（`*mwrite` / `*mread` / `*mmul`）、nop、PE メモリのハザード
- **M2:** L1BM↔PE、L2BM↔L1BM（`l1bmp` / `l1bmd` / `l1bmm` / `l2bmb` / `l2bmd` / `l2bmr` など）とそのハザード
- **M3:** MV 命令による DRAM / PDM / L2BM 間の転送（`mvp` / `mvb` / `mvd` / `mvr` 系）と `wait`

## 5. 表示

### 5.1 ズームによる粒度の切り替え

| ズームレベル | 表示 | 表現 |
|---|---|---|
| チップ全体 | DRAM / PDM / L2BM ×8 / L1BM ×64 | 経路の太さと粒子の密度で、転送量を表す |
| L2B / L1B | 選択したブロックの子ユニット | ユニット単位の流れ。bcast や reduce の分岐・合流が見える |
| MAB / PE | 選択した PE の内部 | ワード単位。アドレスの格子、ALU / MAU、フォワーディング経路、値を表示する |

- 表示中のレベルの要素だけを DOM に置き、4,096 PE を常時すべて描画することはしない。
- 隣り合うレベルの間は、拡大・縮小のアニメーションでつなぐ。
- PE レベルでは、選択した値の来歴の経路を強調表示する。

### 5.2 時間軸

- ステップ単位のタイムライン（再生、一時停止、コマ送り、シーク、再生速度）。ステップを展開すると4サイクルの内訳を表示する。
- 公式スコア（`j` + `m`）を常に表示する。nop の割合と、競合の種類ごとの内訳も表示する。
- 転送量と稼働率をスパークラインで示し、混雑しているステップをすぐ見つけられるようにする。
- タイムラインの各ステップは、VSM の該当行とハイライトで連動させる。

### 5.3 二つのモード

1. **Explorer モード**（デバッグ・性能分析）
   - VSM とテストケースを、`problems/` から選ぶかドラッグ＆ドロップで読み込む。
   - タイムラインで操作し、ユニットやアドレスをクリックすると、値の来歴と数値を表示する。
   - 競合の一覧（nop の理由、削れる候補）と、階層ごとの集計を表示する。
2. **Story モード**（学習・説明）
   - スクロールに合わせてアニメーションが進むスクロールテリングにする。
   - 説明文の各節に「どのイベント列を、どのズームレベルで見せるか」を割り当てる。
   - 題材は `problems/` の実際の問題から選ぶ（6章）。

## 6. Story モードの題材

| 順番 | 問題 | 見せたいこと |
|---|---|---|
| 1 | `3.relu` など PE 内で完結する問題 | PE 内の値の流れ、ALU、フォワーディング、nop が必要な理由 |
| 2 | `17.dram-dl-256-16` / `18.dram-ul-256-16` | DRAM → L2BM → L1BM → PE への分配と回収 |
| 3 | `39.matmul-trb-pkg-lmdram-256-1024-16` | 大きな行列の分配と、MAU による行列積のパイプライン |

## 7. 技術スタック

| 役割 | 採用 | 理由 |
|---|---|---|
| ビルド | Vite + TypeScript | パーサ、シミュレータ、イベントの型を厳密に書ける。静的サイトとして出力できる |
| UI | Svelte 5 | SVG を宣言的に書きやすく、ランタイムが軽い |
| アニメーション | GSAP（ScrollTrigger / MotionPath） | 複雑なタイムラインの合成とスクロール連動の定番。全プラグインが無料 |
| レイアウト計算 | d3-scale / d3-hierarchy | ツリーの配置と量のスケーリング |
| テスト | Vitest | パーサ、シミュレータ、ハザード判定の単体テスト。`problems/` の VSM と公式アセンブラの出力で照合する |
| 公開 | GitHub Pages | 静的にビルドしてそのまま公開する |

- 置き場所はこのリポジトリの `viz/` とする。
- 粒子の数が多すぎて SVG で描き切れない場合に限り、粒子の層だけを Canvas で重ねる。どこからそうするかは計測して決める。

## 8. 非機能要件

- `fx_export` の出力（10万行規模）を読み込んでも、解析が数秒以内で終わる（解析は Web Worker で行う）。
- 通常のズームレベルで 60fps を目標にする。
- 新しい命令への対応は、パーサ、シミュレータ、ハザードそれぞれの規則表に1項目足せば済むようにする。

## 9. スコープ外（当面）

- MV 命令の実行サイクル数の推定（仕様上、静的には決まらない）。
- エミュレータの内部状態の取り込み。照合には `d get` の出力だけを使う。
