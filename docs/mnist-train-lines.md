### わかったこと: UL→DL はコピーではなくレイアウト変換

以前は「UL が書いたテンソルを DL がそのまま読み直しているだけ」と考えていたが、違う。
オペレータごとに LM のレイアウトが違い、境界の DL が `mvp`/`l2bmd`/`l2bmb` で
L2B 複製を作り直している。例:

- `Exp` の出力 `_exp`: `((8_L2B:1, 4:2, 8_L1B:1), (2:1, 4_PE:1, 2_W:1))`、len=16
- `Div` が読む `_exp`: `((4_L2B:2, 64:2), (2:1, 4_PE:1, 2_W:1))`、len=256

同じ [256,16] でも LM 上の配置が違い、その変換が DL の仕事になっている。
実験でも確認した。

- UL+DL を LM1→L1BM→LM0 のコピーに置換 → 1,056,256 ワード中 5,993 ワードが不一致。
- UL の mvp と DL の mvp を L2 往復に置換 → 同じく 5,993 ワード不一致。

つまり往復を消すには、オペレータ間でレイアウトを揃える（またはオンチップで
再レイアウトする）必要がある。これは 1 オペレータの置換では済まない。

### 効きそうな順

     softmax 鎖（5 オペレータ）や ReLU マスク鎖を 1 オペレータにできる。

## DL/UL の中身を計測した（2026-10-20 追加）

`viz/core/src/bin/lm_dump.rs` を追加した。VSM に `d get` を挿すと、シミュレータの
LM/GRF の内容をそのまま出せる。これで分かったこと。

1. **DL/UL は LM 視点では純コピー。**
   `Add` の出力（LM1）と、その UL+DL 後の LM0 を 4 PE で比較すると全ワード一致した。
   配置（MAB/PE 分配）は LM レイアウト文字列のとおりで、DL が勝手に並べ替えているわけではない。
2. **UL の `dmwrite`/`dmread` 経路は 4 ワード単位の並べ替えをする。**
   `l1bmm` 直接に置き換えると `_sum_UL` では 32 ワード中 16 ワードが化ける
   （`_max_UL` は偶然一致するが、値の並びに依存するので採用しない）。
   この並べ替えを再現しないと、UL+DL を LM コピーに置き換えられない。
3. **ALU の `v` 書き込みは 4 ワード（2 サイクル）しか書かない。**
   `frelu $n0v $n0n $m0v` で LM0 の 4..7 は書かれず、レプリカ（`2_W:1` の 2 語目）は
   DL が埋める。このためバンク反転（LM1 に書いて LM0 で読む）は、レプリカの扱いが合わず
   1,455〜1,775 ワードの不一致になる。
4. **fc1 は逆伝播の重み勾配 Gemm も DRAM から読む。**
   フォワードのためだけに UL を消すと、逆伝播が古い DRAM を読んで壊れる。

5. **L1BM の中身は UL 直後と DL 直後で完全に一致する。**
   `$lb0` を 512 ワードぶんダンプして比較すると、8 つの L2B/L1B 経路すべてで同一だった。
   それでも「UL の l1bmm の直後に DL の l1bmm だけを置く」と結果が変わる（1,991 ワード不一致）。
   L2 ブロックからの読み直し（`l2bmd` + `l1bmm`）でも同じく不一致。
   **違いを作っているのは `mvp`（DRAM 経由）の並べ替えそのもの**で、
   L2BM の 64 長語ブロックと DRAM のレイアウトは順序が違う（`docs/shortening_techniques.md` 4.3）。
   つまり UL+DL は「コピー + 並べ替え」で、並べ替えを飛ばすと数値が変わる。

6. **命令を 2 行挿しても結果は変わらない（以前の「変わる」は比較ミス）。**
   番兵の `nop` を Relu の直後やプログラム末尾に挿しても、正しいベース
   （同じプログラムの出力）と比べれば 0 差分だった。
   以前 1,991 ワードの不一致が出たのは、融合前の 2,167 行版の出力を
   現在のアドレスで読んでいたため。**比較は必ず同じプログラムの出力に対して行う。**
7. **隣接 UL→DL の DL は、LM レイアウトが同じなら丸ごと省略できる。**
   UL の `l1bmm` が残した L1BM ブロックを、DL の最後の `l1bmm` がそのまま読める。
   5 組で -30 行、実データ 1 step の DRAM 最終状態は 0 差分。
   レイアウトが違う組（`_sub`→`_exp`）は packing が違うので省略できない。
8. **バンク反転（LM1 読み・LM0 書き）も 0 差分で通る。**
   Relu を `frelu $n… $n… $m…` にし、UL を LM0 読みに変えても、
   正しいベースと比べて全ワード一致。応用として、Add の出力（LM1）を Relu が
   直接読み、Relu の出力（LM0）を fc2 の Gemm が直接読む形にすると、
   `fc1_pre` と `fc1` の DL 2 本（16 行）が不要になる（-14 行、0 差分）。
   `tools/tune_train_vsm.py` に手作業ぶんをまとめ、生成 → tune → squeeze の順で再現できるようにした。
10. **レイアウトが違う組でも、DL の mvp/mvb（DRAM 往復）だけは削れる。**
    UL が `l2bm` で書いた L2 ブロックを、DL の `l2bmd` がそのまま読めるため。
    LM レイアウトが同じ組（L1BM 直読み）と違い、L2 ブロックは並べ替え後の中間表現。
11. **単一消費者で隣接する UL+DL は、LM1→L1BM→LM0 のコピーに置き換えられる。**
   そのテンソルを読む DL が直後の 1 本だけで、グラフ出力でもなければ、
   DRAM に書く必要がない。`fc2_pre_matmul` と `grad_fc2_input` の 2 組で -26 行。
   グラフ出力 9 本は 0 差分（消した中間テンソルの DRAM だけが古いまま残る）。

### 帰結（転送について）

DL/UL は無駄なコピーではなく、**オペレータごとに違うレイアウトを DRAM 往復で変換する装置**。
1 組あたり 8〜17 行のうち、並べ替え（mvp 4 語 + 待ち）が主要コストで、これは省けない。
転送を大きく減らすには、オペレータ間で LM/DRAM のレイアウトを統一して
並べ替え自体を不要にする（＝カーネルと変換器の設計変更）しかない。

## これ以上下がらない理由（2026-10-20 時点の結論）

現在 1,446 命令（raw 2,090、アセンブル後 1,618 語）。ここから 500 まで下げる道は、
次の 3 つの実験で塞がっている。

### 実験 1: UL+DL を LM→LM コピーに置換（失敗）

UL の L1BM ブロックをそのまま DL の l1bmm で読み直す。1,056,256 ワード中 5,993 ワードが不一致。
L1BM ブロックと、DL が期待する L2BM/DRAM 像は同じではない。

### 実験 2: UL の mvp と DL の mvp を L2 往復に置換（失敗）

同じく 5,993 ワード不一致。DRAM を挟む `mvp` は単なるコピーではなく、
PDM 経由のレイアウト変換を含む。

### 実験 3: バンク反転でインプレースに書く（失敗）

`Relu` の出力を LM1 ではなく LM0 に書き、消費側の DL を消す。
- `fvadd $m0v … $m0v` のような同一アドレスの読み書きは LM0 ポート競合で assemble3 が拒否。
- `fvadd $m0v … $m32v` のような別アドレスは命令フィールド競合で拒否。
- `frelu $n0v $n0v $m0v`（LM1 読み・LM0 書き）は assemble3 を通るが、
  1,775 ワードが不一致。DL はデータの配置（MAB/PE への分配）も作っており、
  計算カーネルの出力をそのまま置いても同じ配置にならない。

### 実験 4: ReduceMax の出力を直接 LM0 に置く（失敗）

最大値の UL（38 行）と DL（13 行）を消すため、`ReduceMax` の書き込み先を
LM0:256（`Sub` が読む場所）に変えた。assemble3 は通るが 1,999 ワードが不一致。
DL が作る配置は、計算カーネルが同じ番地に書いただけでは再現できない。

### 追試: nop 除去の全数探索（シミュレータ検証）

`nop` と `nop/N` の全 104 箇所を 1 本ずつ外し、assemble3 と
`cpu_step` の出力一致の両方で確認した。**安全に外せるものは 0 本**だった。
`nop/3` は L1BM→L2 の 10 サイクル待ちで、機械的に消すことはできない。

### 帰結

- 転送 979 行のうち、消せるのは「1 オペレータ内で中間値を保持する」融合だけ。
  これは SGD 更新・損失勾配・ReLU マスクで実績があり、1 組あたり 17〜100 行。
- 残っている同レイアウトの組は 12 組（各 17 行前後）だが、Gemm/OneHot を跨ぐものは
  カーネル内部の配置まで合わせる必要があり、1 組ずつ手で書くしかない。
- 全部消しても 1,446 − 300（融合）− 100（計算ゴルフ）≈ 1,050 行。
  500 はこの下限のさらに半分で、データ配置の層を作り直すか、仕事量
  （バッチサイズ・出力するテンソル）を変える以外に届かない。

### 500 に近づける選択肢（仕事量を変える）

1. バッチサイズを 256 → 64 にする。入力 DL・GEMM・活性化が 1/4 になり、
   素朴に見積もって 1,050 → 800 行程度。ただし 64 行用の GEMM カーネルが要る。
2. 学習に不要な出力（勾配 4 本・output）を書かない。ただし現状の変換器は
   中間テンソルも UL するので、出力指定を変えるだけでは行数は減らない。
3. 配置レイヤを作り直す（DL/UL を LM バンクの ping-pong に置き換える）。
   これが本来の解決策だが、全オペレータのカーネルをバンク非依存にする大工事。

## 試して駄目だったこと（2026-10-20、その 3）

- **SumDiv の再挑戦。** ReduceSum の書き込み先を LM0:256 に変え、和の UL と DL を
  消すと、PE0 では DL 後の配置と完全一致（32 ワード）したが、MAB が変わると
  一致しない（PE `n1c0b0m3p1` で 2 ワード、`n2c1b3m7p2` で 32 ワード）。
  ReduceSum は各 PE の行和を LM1 に書くが、DL は DRAM 経由で PE ごとに
  再分配している。T 間接で読む Div には、この再分配をカーネル内で
  再現する必要がある。リバート。

## 試して駄目だったこと（2026-10-20、その 2）

- **重みの LM ピン留め。** fc1 重みを forward DL のあと LM0:448 にコピーし、
  SGD の param DL（47 行）をそこからのコピーに置き換えた。assemble3 は通るが、
  forward の重みレイアウト `((8_L2B:1, 32:2), …)` と SGD の param レイアウト
  `((16:1), …)` が違うため 8,064 ワードが不一致。ピンを使うには
  テンソルごとのレイアウト統一が要る。
- **単一消費者コピーの nop を 1 個に。** L1BM 読み出しの前に 2 サイクル必要で、
  1 個にすると assemble3 が DataRace で落ちる。

## softmax の融合（2026-10-20）

- **`MaxSub`（`x - max(x)`）は成功。** ReduceMax の書き込み先を LM0:256 に変えると、
  SubRow がそのまま読める。最大値の UL（38 行）・DL（21 行）・ReduceMax（21 行）が
  1 オペレータに畳まれ、グラフ出力は 0 差分。
- **`SumDiv`（`exp / sum(exp)`）は失敗。** ReduceSum の出力を LM0:256 に置いても、
  DivRow は `$mt256v`（T 間接）で和を読むため配置が合わず、probs が 504 ワードずれる。
  T 間接のアドレス対応を再現する必要がある。リバートした。

## Identity の除外（2026-10-20）

グラフ出力の別名 `Identity` は命令を出さないが、直前の `nop/3`（1 命令）と
6 行のコメントを消費していた。生成時にスキップすると、実データ 1 step の
DRAM 最終状態は 0 差分のまま、命令 -9・raw -72 行。

## GEMM の差し替え（2026-10-20）

問題の 1 位解をそのまま貼れる形で 3 本を差し替えた。演算の順序が同じなので、
実データ 1 step のグラフ出力は 0 差分だった。

| オペレータ | 旧 | 新 | 出どころ |
| --- | ---: | ---: | --- |
| `Gemm_15`（grad_fc2_input） | 41 | 13 | problems/42（notr 256_16_16） |
| `grad_fc2_weight_gemm` | 62 | 25 | problems/46（tra 16_256_16） |
| `fc1_pre_gemm` | 32 | 32 | problems/39（trb 256_1024_16）。待ち行が付くので行数は同じ |

### half 精度の採用（10/20）

`fc2_pre_gemm` は問題 36 の 1 位解が half（`hbfn/9` + `hmmul`）の 6 行。
これまでの G 版は 25 行だった。実データ 1 step で probs の差は最大 4.5e-6
（スケール 7.6e-2 に対して相対 ~6e-5）、勾配・更新後の差はさらに小さい。
`gpu_coverage` は MAU/ALU/行列とも全対応（half の行列演算を含む）。

差し替えなかったもの:

- `fc2_pre_gemm`（trb 256_16_16、25 行）: 1 位解は **half 精度**の 6 行で、
  G 精度に直して試すと probs が最大 1.4e-3（相対 ~2%）変わる。ビット一致を
  崩すので採用しなかった。
- `grad_fc1_weight_gemm`（77 行）: すでに problems/48 の 1 位解と同一カーネル。
  97c6f81 で足した行列面クリアの 10 行だけが上乗せ。

## 再生成と検証の手順

```sh
# 1. ONNX を出す（学習率は毎回わずかに変わる。下の注意を参照）
python3 haribote_graph_compiler.py export scratch/train_step --example train_step --ignore loss

# 2. VSM を生成
python3 - <<'PY'
from fx_export.compile import generate_vsm_from_onnx
open('scratch/train_step/train_step.vsm', 'w').write(
    generate_vsm_from_onnx('scratch/train_step/mn_model.onnx'))
PY

# 3. アセンブル（ハザード検査込み）
./judge/judge-py/mncore2_emuenv/assemble3 --instruction-mode flat \
  < scratch/train_step/train_step.vsm > /dev/null

# 3.5 assemble3 が通る範囲で不要な nop を削る（ベンチマークに適用済み）
python3 tools/squeeze_nops.py viz/core/benchmarks/mnist_train_step.vsm

# 4. 実データ 1 step を CPU で実行し、出力テンソルを比較
./viz/core/target/release/cpu_step research/experiments/mnist-gpu scratch/train_step/train_step.vsm
cp research/experiments/mnist-gpu/cpu_final.bin /tmp/new_final.bin

# 5. GPU バックエンドの対応状況
./viz/core/target/release/gpu_coverage viz/core/benchmarks/mnist_train_step.vsm
```

## 注意

- **lr 定数は再生成のたびに下位ビットが変わる。** `fx_export/export.py` が
  `(update / grad).abs().mean()` で学習率を推定しており、プローブの乱数に依存する。
  現在のベンチマークは `0.009999435395002365`。旧ベンチマークは `0.009999952279031277`。
  新旧の出力比較をするときは、`imm` の定数を揃えてから実行する。
  固定したいなら `learning_rate` を 0.01 に決め打ちする変更が要る。
- 旧ベンチマークは 97c6f81 の GEMM 行列面クリアを含んでいなかった。現在は反映済み。
- `research/experiments/mnist-gpu/train/train_fixed.vsm` は 100 epoch 実行時の成果物で、
  fc1 側 GEMM のクリアが入っていない。再学習するときは再生成が必要。
- GPU 実機がこの環境に無いため、`gpu_run_program` と 100 epoch の再実行は未検証。
  `gpu_coverage` は全命令が対応と報告している。
