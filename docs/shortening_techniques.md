# 解答を短くするのに効いた方針

問題48（matmul_tra_pkg_lmdram_16_256_1024）を 140 から 61 に縮めたときと、全問題から不要な nop を削ったときに効いた方針をまとめる。
ここに書いた制約は、どれも公式の assemble3 または judge で確認した。

## 1. スコアの数え方

- スコアは `j + m`、つまり PE 命令語の数と MV 命令語の数の和である（`judge.py` の `--instruction-mode flat`）。
- MV 命令は PE 命令と同じ行に詰められず、1命令がそのまま1語として数えられる。
  MV を分割して転送と並行に流すと、その分スコアが増える。
- `nop/<n>` は n 語と数えられる。

## 2. 下限を先に見積もる

詰める前に、どの資源がボトルネックかを数える。
問題48では次のようになった。

| 資源 | 必要なステップ数 | 理由 |
|---|---|---|
| `l2bmd`（L1BM → L2BM） | 32 | 各 L2BM が部分和の C（8192 長語）を受け取り、1ステップに 256 長語しか運べない |
| MAU（mwrite / mread / calc） | 22 前後 | 1ステップに使える MAU グループは2つまで |
| mwrite グループ | 18 | 最初の4行を確定させるまでの依存の鎖。B の転置 4 chunk × 2、行列のロード 4 × 2、A の転置 2 |
| MV | 5 | `mvrffadd` 1つと、グループごとの `mvp` 4つ |

最終的な内訳は、`l2bmd` を始めるまでの 23 行 + `l2bmd` 32 行 + nop 1 行 + MV 5 語 = 61 である。
`l2bmd` を始める前の行数を、最初に確定させる行のための依存の鎖が決めている。

## 3. 効いた手法

### 3.1 行のグループごとに確定させ、L2BM への転送と重ねる

- k 方向（縮約）を外側のループにすると、全ての行は最後の chunk で同時に確定する。
  そうなると、32ステップの `l2bmd` が計算の後ろにそのまま付く。
- 4行ずつのグループに分けて最初のグループを先に確定させれば、`l2bmd` をそこから流し始められる。
  残りのグループは、`l2bmd` が先行する行を運んでいる間に計算すればよい。
- `l2bmd` は1行あたり2ステップかかる。
  そのため、後続のグループが確定するまでに 8 ステップずつ余裕がある。
- 確定した行は、次のステップで `l1bmd $mauf $lb…` を使って L1BM に集める。
  集めた4行は、L1BM 上の連続する4つの 64 長語ブロックに入る。
- 行の並べ方は `l2bmd` の `$lb` / `$lc` アドレスで自由に指定できる。
  そのため、どの行を先に確定させてもよい。

### 3.2 全 MAB で同じデータの処理は、MAB ごとに分担して L1BM 経由で配る

- A は全 MAB に同じものが置かれているので、それぞれが全部を転置するのは無駄である。
- T 間接参照を使えば、MAB ごとに読み出し位置をずらせる。
  `ipassa $mabid` → `iadd $aluf $aluf $t` で T に 2 × MAB 番号を入れ、`gmwrite $lmt0v16 …` で読む。
  これで MAB m は A の別のブロック（chunk c、上半分か下半分かの h）を転置する。
- 転置した結果は `l1bmd $aluf $lb…`（収集）で L1BM に集め、`l1bmm $llb… $lls…v`（2長語の 16x1MAB 放送）で全 MAB に配る。
  放送1ステップで 8 本のベクトルが届き、8ステップで 64 本すべてがそろう。
- L1BM 側の命令は MAU と別のグループなので、MAU の作業と同じ行に並べられる。
- ここで使う chunk（行列レジスタに載せる k の 8 個組）は、連続していなくてもよい。
  `k = c + 4r` のように飛び飛びにすれば、アドレスの計算が簡単になる。

### 3.3 部分和は `$mauf` で直接つなぐ

- 同じ行のグループを続けて計算するときは、`gmfma … $mauf …` で前のステップの結果を足し込む。
  こうすればメモリへの書き込みも、書き込み後の待ちも要らない。
- つなげられないところだけをメモリに置く。
  最初のチャンクは `gmmul`、最後のチャンクは `$nowrite` にし、確定値は `$mauf` から L1BM に集める。

### 3.4 行列レジスタの2面を交互に使う

- 転置の作業と、計算に使う行列のロードを x と y の2面で交互に回す。
- 同じ行で同じ面に2回触れることはできない。
  `gmwrite` と `gmread` を同じ行に置くなら、別々の面を使う。
- 一度転置した B を BF 化したもの（Bᵀ）は GRF0 に保存しておく。
  行列を何度載せ替えても、転置をやり直す必要はない。

### 3.5 メモリは役割ごとに分ける

| 置くもの | 置き場所 | 理由 |
|---|---|---|
| A, B（入力） | LM0 | 序盤に読むだけ |
| Bᵀ（BF 化済み） | GRF0 | ALU が書いて mwrite が読む。GRF は別アドレスなら同じ行で読み書きできる |
| 放送された A のベクトル | GRF1 | L1BM → PE が書いて calc が読む |
| 途中の部分和 | LM0 / LM1 | 書いてから3ステップ以上後に読む位置にだけ置く |

### 3.6 nop はハザード解析で削る

- シミュレータのハザード解析（`viz/core` の `hazard.rs`）が、各 nop をどの規則が必要としているかを出す。
  どの規則にも必要とされていない nop を1つずつ削り、judge で確認した。
- この方法で 10 問が 1〜13 行ずつ縮んだ。
  例：問題48は 153 → 140、問題27は 43 → 41。

## 4. 詰めるときに当たる制約

### 4.1 同じ行に並べるときの条件（SDM 3.6.4）

- 同じ行では、1つのメモリへの書き込みは1命令まで。
  例えば、`gbfn … $lr…` と `gmmul … $lr…` は同じ行に置けない。
- 同じ行で同じメモリを複数回読むなら、全サイクルで同じ領域でなければならない。
  1命令の中でも同じで、`gmfma $ly $ls0v $ls8v …` は弾かれる。
- LM0/LM1 を同じ行で読み書きするなら、読み書きは同じ領域でなければならない。
  GRF では異なるアドレスで構わない。
- MAU は、calc / mwrite / mread のうち 2 グループまで同時に使える。

### 4.2 ハザード（SDM 3.6.3）

- LM0/LM1 に書いた後は、アドレスに関係なく2ステップ空けないと読めない（ポート衝突）。
  頻繁に読み書きする値は GRF に置く。
- GRF と T は、書いた後に1ステップ空ければ読める。
  `$t` に書いた直後に `$lmt…` で読むことはできない。
- PE → L1BM の後に L1BM → PE を行うには、2ステップ空ける必要がある。
  A を集めてから放送を始めるまでの待ちは、これで決まる。
- PE → L1BM の後に L1BM → L2BM を行うには、10 サイクル空ける必要がある。
  集めてから `l2bmd` を始めるまでの3ステップは、これで決まる。
- L1BM → L2BM の後に、L2BM を読む MV を発行するには1ステップ空ける必要がある。
  最後の nop はこのために要る。

### 4.3 MV で DRAM のレイアウトを直接作れなかった理由

- `mvrffadd` で L2BM から DRAM に直接書くと、DRAM の 16 長語単位がグループ間で交互に並ぶ。
- 一方で `l2bmd` は、L2BM 上の 64 長語ブロックの中に L1B の番号順でデータを並べる。
- この2つの並びは両立しない。
  そのため、PDM を経由して `mvp` を4回使う構成（MV 5語）のままにした。

## 5. 作業の進め方

- スケジュールは Python で生成した（`docs/scripts/p48_schedule.py`）。
  各行の命令をステップ番号つきで並べ、アドレスはこのスクリプトで計算する。
- 生成した解答は、毎回次の3つで確かめた。
  - シミュレータ（`viz/core` の `viz_trace`）：数値と、ハザードの違反。
  - assemble3：同じ行に並べるときの条件と、アセンブラ自身のハザード検査。
  - judge：最終的な判定。
- シミュレータは、同じ行に並べる条件（SDM 3.6.4）と T 間接参照のハザードも検査する（`issue.rs`、`hazard.rs`）。
  ただし MV の発行タイミング（3.6.3.1）は近似で、アセンブラと結果が食い違う場合がある（問題18）。
