# 仮説と実験

形式: 仮説 / 方法 / 結果 / 未解決。日付順に追記する。

## H0: nop 8 語は除去できるか
- 方法: 93 語解の `nop` 行（63,67,71,74,85,87,88,91）を個別に削除し、ネイティブシミュレータで検証。
- 結果: **シミュレータでは全て削除可能（各 -1 語、不一致 0）**。しかし公式アセンブラのハザードチェッカが全件拒否
  （T レース / GRF1 / L1BM / mvd 前）。`tools/fbasm.py` で再現可能。
- 未解決: nop 行を「空ける」のではなく「有用な式で埋める」余地。imm の移設は 88 候補試して全滅（issue/ハザード）。

## H1: 2 ブロック/PE でレンダリングを償却できるか
- 事実: 配送尾部は 2 ブロック/PE で実測成立（packer `p12_final_2block.vsm`、DRAM[b]/[b+2048] 各 2048/2048 一致）。
- 疑問: レンダラは PE 並列で全 4096 PE が同一式を実行するため、active PE を 2048 に減らして 2 ブロック/PE にしても
  (PE, block) 対の総数は 4096 のまま。式の本数が減る理由が見えない。
- 判定待ち: packer に (a) ブロック毎コストの内訳 (b) 消える語 (c) L1BM の 64 long/PE 制約が改善するか を数値で要求。
- 親の現時点の見立て: **語数削減にはならない可能性が高い**。本線は ALU 式 66 → 50 の削減。

## H2: T連鎖の閉形式化（digit-closedform）— 否定
- 訂正: 「11 ALU 連鎖」は実際には **6 ALU + 6 MAU**（L42-48）。削減上限は 6 ALU。
- 厳密意味論を確定（verify_chain.py, 4096/4096）:
  `w = digits+1`, `M = 8w+39`, `C = {2:8,3:13,4:66,5:599}`, `r18 = (s0+C_w) mod M`,
  `k = #{i: r18 >= T_i}`, `T = 0x4b000000 + 2k`（T は L77 まで T 間接 LM0 アドレス）。
- 閉形式は全滅（アフィン床・差の床・min/max の床を総当たり）。剰余表は `r18>>3` だと 3010/4096 で誤り
  （mod M の巻き戻しのため）。w 依存8ブロック表でも 1240/4096 誤り。直接表は約79エントリ必要だが
  MAU は1命令4語しか書けず、空きも足りない。
- 最良の壊れた候補: `cand_table_keep51.vsm` 91 語 / 2718 不一致。L51 `fftoi` は live（削除禁止）。

## H3: 2候補/ブロックの2ブロック化 — 前提が否定
- 8バイト語に交差する数値の個数: 1個=104語, 2個=2446, 3個=1543, 4個=3。
- 2候補では **759 語（1174 バイト）** が誤り。補正パスは SIMD 1回分のコストで、小さな例外集合ではない。
- **3候補/ブロックで全4096語をカバー可能（例外0、全数検証）**。4サイクル×4レーン=16レーンに
  `ll`（2長語）オペランドで 6候補×2レーン=12 ≤ 16 が入る見込み。検証中。
- 2ブロック尾部は +1 語（16→17）。ゲインはスカラー鎖の共有からのみ出る。

## H4: 2候補/ブロック（twoblock 訂正版）— 前提は満たすが 2 ブロック化は純損失
- 数字を所有する数値は 1 語あたり最大 **2 個**（0個:580, 1個:2466, 2個:1050, 3個以上:0）。
  93 語解の 8 桁レジスタはまさに「2数値×4桁」。4 候補目は不要（オフセット3 は出現せず）。
- しかし ALU の演算レーン幅は 1 命令 = 8 int32。`ll` オペランドは算術を広げない
  （`iadd $llr0 $lls0 $lls16` は LSB 長語素通り）。1 ブロックで 8 レーン使い切るため、
  2 ブロックでは digit 段が 2 命令になる。
- 再見積り: 2 ブロック = 76 ALU + 尾部17 = 93 語解より **+11 語の純損失**。→ ルート廃止。
- 残る本線: **単独 imm 行の除去**（del_18 で 92 語・22 バイト誤りまで実測済み）。

## H5: 単独 imm 行の除去（constants）— 92 語まで到達、そこから先が不可能と判明
- `del_18.vsm` = **92 語**、ハザード通過、公式 judge **32744 correct / 22 mismatch**（DRAM word 0..2）。
- 定数 32 の代替生成を全数試行して失敗:
  1. 92 行すべてへの移設 → L86/89/90 のみアセンブルだが消費者 L24 より後。L24 以前に空き ALU スロットは無い。
  2. MAU 生成 → MAU に即値オペランドは無い。L19/L20 で作れる最大は 20.0。32=8*4 は L20 の mauf 鎖＋`fftoi` が要り、
     L21-L25 に 3 つ目の MAU スロットが無い。
  3. 既存 imm の再利用 → L2 の 56 は bit mask 0x38 で live（32 に置換すると 3567 語誤り）、L3/L15/L22/L23/L27 も live。
  4. パラメータ統合 → s29:=8 で 51 誤り、s28:=13 で 4096 誤り。
- 他 9 行の削除コスト: L14=4096, L19=50, L20=581, L26=4089, L30=532, L31=3512, L49/56/78 は必須スペーサ
  （T/GRF1 レース）。L56 の値は dead だが GRF1 スペーサ。
- 副産物: canvas マスク omr15 の値 5 は L56 で無料再生成可能（`u`-imm の x,0,x,0 パターン由来）。
  ただし `/0101` リテラルは非等価（4096 誤り）。

## H6: 転送行への ALU 同居 — 合法だが使えない
- 実測: L86/L89/L90 の `l1bmd`/`l2bmd` 行は ALU 式を同居させられる（`assemble3` ASM-OK、3/3）。
- しかし転送行は全て消費者の後ろにあり、そこで計算しても出力は変わらない。
  定数 32 を L86/89/90 に置く案（constants の (c)）も同じ理由で無効。
- 2目的地 ALU 式（`ilsl $aluf $r4 $s0/1000 $r0/1000`）も ASM-OK を再確認。
- 結論: 空きスロットは「存在するが時系列的に手遅れ」。L24 より前に 1 語空ける必要があり、
  それは座標鎖（9 本の逐次 ALU）を短縮する以外にない。

## H7: 座標鎖 L5–L13（9語）の正体 — マスクエントリ 4–7 のクリア
- 実測: L5–L13 を丸ごと削除すると **84 語でアセンブル通過**（`research/experiments/parent/dead_chain_84.vsm`、hazard OK）。
  ただし出力は 4095 語誤り。
- 差分の所在: OMR のワード 4..7 が変化する。
  baseline = (4:0, 5:0, 6:0, 7:0) / 削除版 = (4:15, 5:3, 6:3, 7:3)。
  つまり鎖の役割は **マスクエントリ 4–7 をクリアすること**。メモリ（GRF0/GRF1/LM0）は一切変えない。
- `$aluf` 連鎖は L14 の `imm` では上書きされず、L15 の `hvpassa -$aluf $omr15` が鎖の結果を消費する。
- 次の問い: 「4 つのマスクエントリを 0 にする」を 1–2 語で実現できるか。できれば 93 → 84〜86。
  候補: `imm` + `hvpassa` を既存行に同居、または初期状態が 0 であることを利用して書き込み自体を不要にする
  （ただし削除版では 15/3/3/3 になっており、これは「鎖が書いていた値」ではなく「鎖が抑止していた書き込み」の可能性）。

## H7 追記（ラウンド3）: 鎖の出力は PE 依存、マスク状態は PE 非依存
- L13 直後の `$aluf` を `lpassa $aluf $lm0v` で取り出して測定:
  - PE n0c0b0m0p0 → `0x0000000000000000`
  - PE n1c1b7m15p3 → `0x00007df800000003`（全 4 サイクル同値）
  → 鎖の出力は **PE 依存**。
- しかし L15 後の OMR 全 256 エントリは **6 つの多様な PE で完全一致**（差分 0）。
  → `hvpassa -$aluf $omr15` は鎖の値を潰して定数マスクにしている。
- L5–L13 を削除すると 84 語でアセンブル通過するが 4095 語誤り。差分は OMR ワード 4..7
  （baseline 0,0,0,0 / 削除版 15,3,3,3）。
- 1 行置換（`zero $nowrite`, `imm i"0" $nowrite`, `ipassa $r0 $s8`, `lpassa $ls0 $lr8`,
  `ipassa $r0 $s0/1000`, `ior $r0 $s0v $s8`）はすべて 85 語・4095 誤り。
  `$nowrite` は forwarding を更新しないため、置換行が aluf を作れていない可能性が高い。
- 部分保持（末尾 k 行）は k=1..3 で 85..87 語・4096 誤り、k=4..8 はアセンブル失敗。

### 次の具体的な問い
1. OMR ワード 4..7 は実は「エントリ 1 の 4 サイクル」ではないか（ダンプのアドレス/サイクル対応を確定する）。
2. プログラム中で `$imr1` を読む行（L39 付近）が要求する値は何か。エントリ 1 を 0 に保つ必要があるなら、
   鎖の代わりに 1 行で 0 を書く手段（OMR への書き込み命令）を探す。
3. 鎖の 9 行は「OMR エントリ 1 を 0 で上書きし続ける」ための遅延＋クリアではないか。

## H7 追記2（ラウンド4）: 9 行は遅延フィラーではない
- L5–L13 を nop に置換: 9/8/7/6/4/2 個のいずれでも **4095 語誤り**。
  → 純粋な待ち行ではなく、値を作っている。
- 鎖の出力は PE 依存（0x0 / 0x7df8...）だが、L15 後の OMR ダンプは PE 非依存に見える。
  この矛盾は「マスク書き込みのセマンティクス（どのサイクル/レーンが実際に書かれるか）」の理解不足によるもの。
  次の測定: `hvpassa -$aluf $omr15` を既知の aluf 値（0, 0x7df8..., 0x80000000）で実行し、
  OMR 書き込み値を直接比較する小さなプローブを作る。
- 削除版・nop 置換版・定数置換版がすべて 4095 誤りという同一の壊れ方をするのは、
  おそらく「マスクが全 PE で同じ値になるべきところ、PE ごとに違う」ためではなく、
  鎖が **別の状態**（forwarding の有効/無効など）も動かしている可能性を示す。

## H7 追記3（ラウンド5）: 鎖の正体は「GRF1 ワード0 への座標ビット詰め込み」
- OMR ダンプの対応を確定: `$omr0` で 4 アドレス、アドレス 0..3 は初期値 15（エントリ0）、
  `$omr15` はアドレス 60..63（エントリ15）。前回「エントリ4..7が変わる」と書いたのは
  エントリ1（アドレス4..7）のことで、これは **L24 が書き込む先**（`isub ... $omr1`）。
- 鎖の本当の出力は **GRF1 ワード0**:
  - PE n1c1b7m15p3: L12 で `0x0000030e00001c10` → L13 後 `0x00007df800001c10`
  - PE n0c0b0m0p0: 0（マスク `/1000` により書き込みなし）
- つまり鎖は座標（l2bid/l1bid/mab/pe）をシフトと OR で 64bit に詰めて GRF1 w0 に書く。
  L13 の `ilsl ... $s0/1000 $r0/1000` が最終シフト＋マスク付き書き込み。
- 削除すると GRF1 w0 が作られず、以降の `$s0` 参照がすべて狂う → 4095 語誤り（整合的）。
- 次の問い: この詰め込みを **2〜3 ALU** で行う方法はあるか。
  候補: `packbit` の連鎖、`$mabid`/`$subpeid` の直接利用、`ilsl` の 2 目的地化。
  座標のビット配置から逆算して、必要最小限のシフト/OR 数を求める。

## H7 追記4（ラウンド6）: 詰め込み鎖の部分削減は不可
- L11 (`ior $aluf $s0 $nowrite`) 削除 → 92 語 / 3966 語誤り
- L12 (`ior $aluf $s1 $nowrite`) 削除 → 92 語 / 3829 語誤り
- L11+L12 を `ipackbit $s0 $s1 $nowrite` に統合 → アセンブラが `in_grf1`/`in_grf1` のポート衝突で拒否
- 鎖の各項は最終値に寄与しており、単独削除では壊れる。統合はポート制約で阻まれる。
- 残る道: 座標の詰め込み式そのものを別の演算（固定値オペランド `$msb1` など）で置き換える。
  そのためには各 PE の目標値（例: l2b=1,l1b=7,mab=15,pe=3 → 0x7df800001c10）を
  座標の関数として同定する必要がある。

## H7 追記5（ラウンド7）: 座標詰め込み写像のサンプル
L13 直後の `$aluf` を 12 PE で採取（`lpassa $aluf $lm0` で取り出し、アドレス0 = サイクル0）:

| (group,c,l1b,mab,pe) | 64bit 値 | 上位32 | 下位32 |
|---|---|---|---|
| 0,0,0,0,0 | 0x0000000000000000 | 0 | 0 |
| 0,0,0,0,1 | 0x0000000800000000 | 8 | 0 |
| 0,0,0,1,0 | 0x0000002000000000 | 32 | 0 |
| 0,0,1,0,0 | 0x0000004000000000 | 64 | 0 |
| 0,0,0,0,3 | 0x0000001800000000 | 24 | 0 |
| 0,0,1,1,1 | 0x0000006800000000 | 104 | 0 |
| 0,1,2,3,2 | 0x000014b000000001 | 5296 | 1 |
| 1,0,4,5,3 | 0x0000293800000002 | 10552 | 2 |
| 1,1,7,15,3 | 0x00007df800000003 | 32248 | 3 |
| 0,0,7,0,0 | 0x00000c4000000000 | 3136 | 0 |
| 0,1,0,0,0 | 0x0000008000000001 | 128 | 1 |
| 1,0,0,0,0 | 0x0000010000000002 | 256 | 2 |

読み取れる構造:
- **下位32 = l2bid**（= 2*group + c）。0,0,0,0,3,0,1,2,3,0,1,2 と一致。
- 上位32 は加法的な成分を含む: pe=1→8, mab=1→32, l1b=1→64, かつ (1,1,1) → 104 = 64+32+8。
- しかし l1b=7 → 3136（= 64*49 = 64*7²）、l1b=4 → 10552 の一部、と非線形。
  → l1b の寄与は 64*b ではなく、**シフト量レジスタ `$r[0,0,14,8]` 等が座標依存**なため。
- この写像は「座標→(x,y,z) のビットパッキング」であり、座標ごとに 12 サンプルで式を推定できる。
  式が 2〜3 演算で書ければ 9 語 → 3 語前後（-6 語）。

次の手順: サンプルを 32〜64 PE に増やし、上位32 のビット寄与を座標フィールドごとに分離する
（1 フィールドだけ動かしたペアを作る）。そのうえで `packbit` 連鎖または `ilsl`+`ior` 2 本での
再現を試す。

## H7 追記6（ラウンド8）: 座標詰め込みの閉形式を同定
固定値オペランドの実測:
- `$l1bid` = l1b、`$mabid` = mab、`$l2bid` = l2bid（いずれも 32bit 両レーンに複製）
- `$peid` = **mab*4 + pe**（例: mab15,pe3 → 63）、`$subpeid` = pe、`$msb1` = 0x80000000 定数

鎖の出力（サイクル0 の長語）は次で厳密に一致する（12+13 サンプルで検算済み）:

```
lane0 (上位32) = 8 * b
  b = 512*(mabid>>1) + 128*(l1bid>>1) + 32*(l2bid>>1) + 16*(l2bid&1)
      + 8*(l1bid&1) + 4*(mabid&1) + pe
lane1 (下位32) = l2bid
```

これは packer が測定した DRAM ブロック式
`b = 512*(mab>>1) + 128*(h>>1) + 32g + 16c + 8*(h&1) + 4*(m&1) + p` と完全一致。

検算例: n1c1b7m15p3 → b = 512*7 + 128*3 + 32*1 + 16*1 + 8*1 + 4*1 + 3 = 3584+384+32+16+8+4+3 = 4031、8b = 32248 = 0x7df8 ✓（実測 0x7df800000003）

### 短縮の見込み
必要なのは 5 フィールドの抽出とビット配置:
`8b = 4096*(mabid>>1) + 1024*(l1bid>>1) + 128*l2bid + 64*(l1bid&1) + 8*(peid&7)`
- `$peid` が mab*4+pe なので `peid&7` が (4*(m&1)+p) を直接与える（1 演算節約の芽）
- 残り 4 項は各 1 シフト + OR。理論上 5〜6 語で書ける可能性。
- 現在 9 語 → 6 語なら **-3 語**（93→90）。さらに `ilsl` の 2 目的地化で 1 語削れる余地。

## H7 追記7（ラウンド9）: 閉形式を追加 24 サンプルで検証（計 49 サンプル、不一致 0）
ランダム 24 PE（g,c,l1b,mab,pe を一様抽出）で
`((8*b)<<32) | l2bid`（b は前述の式）と実測 `$aluf` が **24/24 一致**。

### 書き換え仕様（次ラウンドの実装対象）
置換対象: L5–L13（9 語）。目標 5–6 語。
必要値:
```
lane0 = 8b = 4096*(mabid>>1) + 1024*(l1bid>>1) + 128*l2bid + 64*(l1bid&1) + 8*(peid&7)
lane1 = l2bid
書き込み先: GRF1 word0（L13 と同じマスク /1000, 第2目的地 $r0/1000）
```
実装上の注意（実測済み）:
- シフト量は定数ではなく GRF0 のランプ（1,1,2,2,3,3,...8,8）から取られ、サイクルごとに異なる
  （L5 は `$r[0,0,12,2]` = サイクル別に 1,1,6,2）。したがって 4 サイクル分を同時に作る必要がある。
- `$peid` = mab*4+pe なので `peid&7` が下位3ビットを直接与える。
- 最終行 L13 は `ilsl $aluf $r4 $s0/1000 $r0/1000`（2 目的地 + マスク）で、これが GRF1 w0 を書く。

## H7 追記8（ラウンド10）: 座標鎖は短縮できない（理論下限 9 語）
閉形式をビット配置に分解すると、必要な演算数が確定する。

```
b = (peid&7)                       bits 0-2   ← 1 op (iand)
  | ((l1bid&1) << 3)               bit  3     ← 1 op (and+shift は別命令)
  | (l2bid << 4)                   bits 4-5   ← 1 op (shift)
  | ((l1bid>>1) << 7)              bits 7-8   ← 1 op (shift)
  | ((mabid>>1) << 9)              bits 9-11  ← 1 op (shift)
```
- `peid = mab*4+pe` なので `peid&7` が下位3ビットを直接与える（1 演算節約になる唯一の箇所）。
- `l1bid` は bit3 と bits7-8 の**2 箇所**に飛び飛びで入るため、1 回のシフトでは両方を正位置に置けない
  （`h<<3` は bit3 を正しく置くが、h の上位ビットが bits4-5 に来てしまう）。→ l1b に 2 演算必要。
- したがって **5 回のシフト/マスク + 4 回の OR = 9 演算**が必要で、現行 L5–L13 の 9 語と一致する。
- つまり座標鎖は**既に理論下限**であり、ここから語数を削る余地はない。

### 結論
「座標鎖を 5〜6 語に短縮して -3〜-4 語」という目論見は**否定**された。93 語解の座標部は最適化済み。
残る削減対象は桁生成（22 ALU）と定数（10 語）のみで、いずれも過去ラウンドで全数試行済み。

## H8: 行列レジスタ経由の定数生成 — 算術ランプしか作れない
- `dmread $lx0 $lr0v4` 1 命令で GRF0 の複数長語を書ける（実測: 3 語）。
- `dmwrite` + `dmread` + `iinc $mreadf` の繰り返しで作れるのは **等差数列のみ**
  （例: subpeid=1 で 1,2,2,4,4,6,6 ... のランプ）。
- 必要定数（32, 408, 4672, 63.0, 1/71, 1/79, 0.001, 0x4b000075）は非等差数列であり、
